## Context

任务列表目前默认展示最近更新的全部任务。随着任务数量增加，已完成或暂不处理的任务会长期占据主列表，降低工作台聚焦效率。

本次需求要求新增“归档任务”能力，并明确以下行为边界：

- 归档任务默认不出现在主列表
- 归档任务只在“已归档”视图中展示
- 归档任务允许后续取消归档
- 归档任务在归档视图中才允许查看和操作

## Goals / Non-Goals

- Goals:
  - 提供稳定的任务归档状态持久化
  - 保持主列表默认仅展示未归档任务
  - 支持查看归档任务、取消归档与删除归档任务
  - 避免对现有任务详情、运行记录、Raw 导出等基础能力造成回归
- Non-Goals:
  - 不实现批量归档
  - 不实现独立归档页路由
  - 不对归档任务增加额外权限模型

## Decisions

- Decision: 任务记录增加 `archivedAt` 字段，未归档为空字符串，已归档时保存 ISO 时间
  - Why: 比布尔值更易扩展，后续可以直接展示归档时间，也便于审计

- Decision: `/api/tasks` 默认仅返回未归档任务，并通过查询参数切换 `active` / `archived` / `all`
  - Why: 由服务端表达“默认不展示”的产品语义，避免前端自行过滤导致数据与排序不一致

- Decision: 复用现有 `PUT /api/tasks/:slug` 更新接口完成归档与取消归档
  - Why: 任务更新能力已经存在，增加一个可更新字段比新增专用端点更简单

- Decision: 运行中的任务禁止归档
  - Why: 如果允许归档，任务可能在用户执行期间从主列表消失，增加状态理解成本，也会影响当前实时更新逻辑

- Decision: 前端列表增加两段式视图切换“进行中 / 已归档”
  - Why: 比额外下拉筛选更直观，符合该需求是主列表信息架构调整而非普通筛选项

## Risks / Trade-offs

- 风险：任务列表默认筛选下沉到服务端后，前端现有刷新逻辑需要同步携带视图参数
  - Mitigation: 将当前任务列表视图状态集中到 `useWorkbenchTasks`，统一通过该状态刷新列表

- 风险：当前选中的任务若被归档，需要决定 UI 如何切换
  - Mitigation: 归档当前任务成功后，如果当前处于“进行中”视图，自动切到下一个未归档任务；若不存在则清空当前选择

- 风险：归档任务详情仍可通过直链打开
  - Mitigation: 本次仅约束工作台列表入口；详情接口保留可读性，前端在“进行中”视图中不主动展示归档任务

## Migration Plan

1. 在任务归一化与持久化逻辑中加入 `archivedAt`
2. 补充列表读取与更新逻辑
3. 更新前端任务列表视图与操作入口
4. 运行回归测试、构建和本地更新流程

## Open Questions

- 当前方案不限制通过 URL 直接打开归档任务详情；如果后续希望完全隔离，需要追加详情访问规则
